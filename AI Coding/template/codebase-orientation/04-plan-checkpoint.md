# Prompt 4: Establish Context and Plan the Checkpoint

Action styling is embedded directly in each block. Text outside fenced blocks guides
the candidate; fenced `text` under **PROMPT TO AI** is sent to AI.

The interviewer may state the task directly or provide only a failure, changed test,
stub, example, benchmark, or incomplete behavior. Every checkpoint uses one durable
scratchpad from context through completion.

## <span class="action-chip action-do">DO YOURSELF</span> One Task File Per Checkpoint

Before each checkpoint, assign an ID such as `T1` and create
`.interview/tasks/task_T1.md` from the matching bug, feature, optimization, or
enhancement/refactor template. You may create it manually or ask the main AI Agent to
seed it:

- [bug template](../checkpoint-task-files/bug.md);
- [feature template](../checkpoint-task-files/feature.md);
- [optimization template](../checkpoint-task-files/optimization.md); or
- [enhancement/refactor template](../checkpoint-task-files/enhancement-refactor.md).

The created task file is the single source of truth for:

- current context, evidence, unknowns, and invariants;
- accepted plan and numbered execution steps;
- latest implementation and validation snapshot.

Do not create separate checkpoint-context or plan files. Before each AI request, name
the current task file; the AI reads it first and updates it as the scratchpad.

### <span class="action-chip action-do">DO YOURSELF</span><span class="action-chip action-prompt">PROMPT TO AI</span> Fast Seed

The templates have no tables. Fill `Task` and any details you already know; leave each
remaining value exactly `TO BE FILLED BY AGENT`. This should take under 30 seconds.
Alternatively, tell Agent mode:

```text
Create `.interview/tasks/task_<id>.md` as a table-free <TYPE> task note with: Type,
Status, Task, Acceptance, type-specific known details, Unknowns, Agent Context,
Accepted Plan, and Latest Snapshot. Keep details I supplied; write TO BE FILLED BY
AGENT for every other value. Create only that file; do not inspect/implement; stop.
```

Any tables in the later Plan response are generated by AI; you never type them.

### <span class="action-chip action-prompt">PROMPT TO AI</span> Default Path: Task Is Clear

Do not run discovery or spawn subagents. In Agent mode, send:

```text
COMPLETE CURRENT TASK. Read the named task_<id>.md, research 00-02, and only relevant
code/tests. The task is explicit: preserve it; do not rediscover or broaden it. Replace
every TO BE FILLED BY AGENT with concise grounded evidence, UNKNOWN, or NOT_AVAILABLE.
Fill Agent Context, including relevant code/path, invariants, and available validation.
Set Behavior trace to NOT_NEEDED unless evidence makes the task ambiguous. If material
context is missing, ask up to three concise questions in conversation, one at a time;
after each answer update the task file and continue. When context is sufficient, set
Status to CONTEXT_COMPLETE. Update only this task file; do not implement; stop.
```

### <span class="action-chip action-optional">OPTIONAL</span><span class="action-chip action-prompt">PROMPT TO AI</span><span class="action-chip action-verify">VERIFY</span> Rare Path: Task Is Unclear

Use this only when you cannot state the task or acceptance confidently. Stay in Agent
mode and send one prompt; you do not launch workers yourself.

```text
DISCOVER UNCLEAR TASK. Read the named task_<id>.md and research 00-02; do not implement.
As parent Agent, internally spawn up to two parallel read-only workers: Signal/Contract
finds what is observed and defines expected behavior; Code-Path follows the relevant
entry, calls, and state. Reconcile them; if spawning is unavailable, do both passes
yourself sequentially.
Use the cheapest available observation: existing output, test/build button, manual
UI/API/sample, diagnostics, or static requirement/test/code evidence. No command is
required; for a new feature or unavailable runner use NOT_AVAILABLE.
Write one line in Agent Context:
Behavior trace: SIGNAL -> EXPECTED SOURCE -> ENTRY -> RELEVANT PATH -> EXACT GAP.
The AI performs the trace so the candidate can verify the cited path and avoid random
search or symptom patches. Consider <=3 candidate tasks. If unresolved, set AMBIGUOUS
and ask one direct scope question in conversation. After the answer, update the task
file and continue. Otherwise fill all placeholders and set Status to CONTEXT_COMPLETE.
Update only the task file; report its path; stop.
```

If Agent mode asks a question, answer it normally in chat. A useful scope question is:

> I see `<signal or requirement>`. Evidence points to `<candidate task>`, with success
> defined as `<acceptance>`. Is that the intended checkpoint and scope?

Have Agent mode record the answer in the same task file.

### <span class="action-chip action-do">DO YOURSELF</span> Form Your Direction Before Plan Mode

Spend 30-60 seconds deciding the acceptance condition, simplest likely approach and
part/flow order, and predicted first check. Prefer existing helpers and direct logic.
Do not ask AI to choose the architecture or strategy.

### <span class="action-chip action-say">SAY TO THE INTERVIEWER</span> State Plan Intent

> "My current approach is `<simple approach/order>`, and `<check>` should prove the
> first part. I will compare AI's bounded plan against this direction."

Immediately before the selected fixed Plan prompt, send only:

```text
CURRENT_TASK: .interview/tasks/task_T<number>.md
```

### <span class="action-chip action-know">KNOW</span><span class="action-chip action-say">SAY</span> Ask-or-Assume Rule

Before coding, process `UNKNOWNS` in order:

1. Remove anything answered by the task wording, failure output, tests, public
   API/schema, or research artifacts.
2. Do not ask when the answer would not change implementation or acceptance.
3. When a conventional choice is reversible in under one minute, state the assumption
   and continue.
4. Otherwise ask one direct question, record its answer in the context/plan, then
   process the next unknown. Ask at most three questions.

Use concrete wording:

- Bug: "Test `<name>` expects `<A>`, but code returns `<B>`. Is `<A>` required for all
  `<scope>`, or only this case?"
- Feature: "When `<conditions>` conflict, which wins? Must current callers/output
  remain compatible?"
- Optimization: "Which workload, metric, and target define success? Which output,
  error, order, mutation, and side-effect semantics must remain identical?"
- Refactor: "Which API and behavior must remain unchanged? Is migration, backfill,
  or compatibility handling required?"

Switch to Plan mode and choose exactly one prompt:

- **Bug fix:** existing behavior is wrong.
- **Feature:** new externally observable behavior is required.
- **Optimization:** behavior stays equivalent while latency, throughput, memory, or
  cost improves.
- **Enhancement/refactor:** behavior is preserved or extended through structural
  change, compatibility work, or maintainability improvement.

### <span class="action-chip action-know">KNOW</span><span class="action-chip action-verify">VERIFY</span><span class="action-chip action-prompt">PROMPT</span> What a Slice Means and What You Do

A **slice** is simply one numbered implementation part. Plan mode returns **all
slices at once in one complete response**, in execution order; it does not wait for
you to request them one by one. A small task uses one slice. Split a large scope by
working behavior such as `Flow 1`, then `Flow 2`, not by technical layers.

- One-slice bug example: `B1 = add regression -> fix root cause -> run all tests`.
- Optional feature example: `F1 = happy path`; `F2 = errors/compatibility`. Each step
   must be independently useful and validated; do not split merely by code layer.

After Plan mode responds:

1. Review the AI's complete Plan response before accepting it; this is your
   **Plan-before-accepting** check.
2. Compare it with your stated direction. Accept a deviation only when requirements,
   code, or test evidence makes it better.
3. Confirm the plan matches the task, covers every acceptance criterion, preserves
   the stated invariants, and orders the implementation parts sensibly.
4. For each slice, verify its `Change` is bounded and its `Check` proves that part.
   Reject unnecessary rewrites, hierarchies, nested class designs, or abstractions.
5. Review the response aloud: state what matches your direction, what looks off, and
   what you accept, reject, or want revised.
6. Ask AI to repair anything missing, vague, or oversized. Then state the accepted
   order to the interviewer.
7. Choose exactly one persistence method below. Do not implement yet.
8. Pass the persistence verification gate.
9. Only then switch to Agent mode and execute one named slice.

#### Required in Every Plan

- acceptance condition;
- 1-3 evidenced invariants;
- all numbered implementation slices in execution order, each with `Change` and
   `Check`;
- full-suite test method after every change; and
- final broad validation and complexity/risk check.

#### Optional Only When Relevant

- multiple slices, dependencies, or rollback;
- alternatives and tradeoffs;
- migration/compatibility/rollout;
- benchmark and accept/reject threshold;
- security, concurrency, persistence, cancellation, or external-failure analysis.

Keep the Plan response compact and omit optional notes that do not apply.

#### <span class="action-chip action-output">AI OUTPUT</span> Complete Plan Response

Plan mode replies once with the entire plan and all slices. Each slice stays short:

```markdown
### <ID>: <flow or implementation part>
- Change: <bounded behavior and likely files/symbols>
- Check: <observable test or result that proves this part>
```

Dependencies, risk, rollback, and budgets belong in brief plan-level notes only when
needed; do not repeat them inside every slice. Before responding, AI verifies that
every requested behavior maps to a slice/check, IDs are ordered, each `Change` and
`Check` is nonempty, and the full-suite rule is present. If anything fails, AI
rewrites the plan first.

The **final line of the entire Plan-mode response**, after all slices and final
validation, must be:

`Plan self-check: PASS`

> [!IMPORTANT]
> No prompt can absolutely guarantee model compliance. The fixed schema plus AI
> self-check makes noncompliance obvious; **VERIFY** and reject or rewrite any
> plan that lacks all slices, the two fields, or the final response line.

## Persist Every Slice Before Implementation

> [!IMPORTANT]
> <strong class="action-chip action-know">KNOW</strong>
> The complete accepted plan must already exist under **Accepted Plan** in the current
> `task_<id>.md` before any source or test file is edited. Persist every slice, not
> only the first slice. This is a hard gate.

### Choose Exactly One Persistence Method

Do **not** perform both methods.

### <span class="action-chip action-prompt">PROMPT TO AI</span> Default: AI Copy

Use this when Agent mode can read the accepted Plan response and write the current
task file. This is normally the faster choice. Send it as a dedicated persist-only
turn:

```text
PERSIST ACCEPTED PLAN ONLY.
Read CURRENT_TASK and the final accepted Plan response in this conversation.
Replace Accepted Plan with that complete response: acceptance, invariants, every
slice in order with Change and Check, the all-tests-after-every-change rule, final
broad validation, complexity/risk, and the final Plan self-check: PASS line.
Do not edit source, tests, configuration, or build files. Do not implement any slice.
Re-read the task file, report the persisted slice IDs in order, and stop.
```

### <span class="action-chip action-do">DO YOURSELF</span> Alternative: Manual Copy

Use this when clipboard/manual editing is available and faster, or when Agent mode
cannot reliably see the Plan response.

1. Copy the final accepted Plan response into **Accepted Plan**.
2. Preserve every slice in order, the full-suite rule, final broad validation, and
   the final `Plan self-check: PASS` line.
3. Replace the previous accepted plan completely; do not append a competing version.

### <span class="action-chip action-verify">VERIFY</span> Persistence Gate

- [ ] **Accepted Plan** contains the final accepted plan, not a summary.
- [ ] Every generated slice ID appears exactly once and in the accepted order.
- [ ] Every slice retains its nonempty `Change` and `Check`.
- [ ] The all-tests-after-every-change rule is present.
- [ ] Final broad validation, complexity/risk, and `Plan self-check: PASS` are present.
- [ ] No source, test, configuration, or build file changed during persistence.

If any checkbox fails, repair the task file before implementation.

### <span class="action-chip action-prompt">PROMPT TO AI</span> Execute After Persistence

Only after the persistence gate passes, start a new Agent turn:

```text
Execute only slice <ID> from CURRENT_TASK.
The complete accepted plan is already persisted; do not replace or summarize it.
Do not start another slice.
After every code or test change, run all available test cases before another change.
Update Latest Snapshot. Report completed or blocked, then stop.
```

If Plan mode later changes any unfinished slice, persist the complete revised plan and
pass this gate again before continuing implementation.

## <span class="action-chip action-output">AI OUTPUT</span><span class="action-chip action-verify">VERIFY</span><span class="action-chip action-say">SAY</span> When the Task Is Complete

This is not another loop.

**Agent mode, at the end of the final slice:**

1. Run the full exposed test suite and any separate build/typecheck again.
2. Verify every acceptance criterion and invariant has evidence.
3. Replace **Latest Snapshot** with `COMPLETED`, changed files, test results,
   complexity, limitations, and residual risk; then stop.

**Candidate (you), after Agent stops:**

1. Inspect the final diff and actual test output.
2. If anything fails or is unexplained, continue the same task.
3. Give a spoken summary to the interviewer: task ID, behavior completed, files
   changed, full-suite result, complexity, and residual risk.
4. Create the next task file, or move to integration when no checkpoints remain.

## <span class="action-chip action-prompt">PROMPT TO AI</span> Plan Mode: Bug Fix

### Full Prompt

```text
PLAN BUGFIX using the CURRENT_TASK file from the preceding message. Read that task
file, research 00-02, and relevant code/tests. If context is missing, conflicting, or
ambiguous, ask up to three concise questions in conversation, one at a time. After
each answer continue planning in chat; do not edit files. The separate persistence
step stores clarified context with the complete accepted plan. Solve that task only.

1. Restate context: task, evidence, expected/actual, acceptance, constraints/non-goals.
2. Rank root-cause hypotheses; select one using evidence and name the cheapest
   available observation that could disprove it.
3. List 1-3 invariants with evidence and a preserving check; identify minimal files/
   symbols and contracts. Reject unrelated refactors.
4. Plan a regression check first, smallest root-cause fix second, then validation.
   Require the full available test suite after every code or test change. A check may
   use a test/Build button, command, or manual flow; record hidden/unavailable limits.
5. Use one slice normally; a second is optional only when there are distinct working
   parts. Name each part by behavior or flow. Under its heading include only `Change`
   (bounded work and likely files/symbols) and `Check` (proof that the part works).
6. Ask <=3 questions only when evidence cannot resolve a costly ambiguity.

Return one complete plan containing all slices at once, in execution order. Each slice
uses `### B<n>: <part>` followed only by nonempty `Change` and `Check` bullets. Before
responding, self-check that every acceptance criterion maps to a slice/check, IDs are
ordered, and the full-suite rule is present; rewrite until valid. The final line of
the entire response is `Plan self-check: PASS`.

Return a chat-only plan, normally <=60 lines; stop. The candidate chooses a slice ID
when invoking Agent mode; do not assign per-slice statuses.
```

### Quick Prompt

```text
PLAN BUGFIX; do only:
1. Read CURRENT_TASK; if context is missing/ambiguous, ask <=3 concise chat questions
one at a time, use answers in chat without editing, then restate expected/actual/
acceptance. Agent later persists the clarified context.
2. Rank causes; choose with evidence/disproof; list evidenced invariants.
3. Plan regression, minimal fix, and all available tests after every code/test change;
use one slice normally, optional second only for a distinct working part.
4. Preserve contracts; no refactors/edits. Return the plan; stop. Candidate names the
slice to execute; do not assign per-slice statuses.
5. Return all slices at once in order. Each uses `### B<n>: <part>` followed only by
nonempty `Change` and `Check`. Self-check acceptance mapping, ordered IDs, and the
full-suite rule; rewrite if invalid. Make `Plan self-check: PASS` the final line of
the entire response.
```

## <span class="action-chip action-prompt">PROMPT TO AI</span> Plan Mode: Performance Optimization

### Full Prompt

```text
PLAN OPTIMIZATION using the CURRENT_TASK file from the preceding message. Read that
task file, research 00-02, and relevant code/tests. If context is missing, conflicting,
or ambiguous, ask up to three concise questions in conversation, one at a time. After
each answer continue planning in chat; do not edit files. The separate persistence
step stores clarified context with the complete accepted plan. Preserve observable semantics.

1. Restate context: workload, baseline, metric, target, measurement, acceptance, and
   non-goals. Mark missing measurements UNKNOWN.
2. Identify the measured or evidence-backed bottleneck; rank optimization hypotheses.
3. List semantic invariants with equivalence tests. Use one experiment slice if enough;
   otherwise optionally decompose into 2-4 parts. Each `Change` covers one major
   variable and likely files/symbols; its `Check` covers correctness, benchmark, and
   accept/reject threshold. Put rollback, dependency, and risk at plan level only when
   relevant.
4. Order baseline/instrumentation first when absent, then lowest-risk/highest-value
   change. Never stack unmeasured optimizations.
5. Require all available correctness tests after every code or test change. Include
   representative/adversarial workloads, complexity/resource impact, and before/after.
6. Ask <=3 questions only when workload, target, or preserved semantics are unresolved.

Return one complete plan containing all slices at once, in execution order. Each slice
uses `### O<n>: <experiment part>` followed only by nonempty `Change` and `Check`
bullets. Before responding, self-check acceptance mapping, ordered IDs,
semantic-equivalence, and full-suite rules; rewrite until valid. The final line of the
entire response is `Plan self-check: PASS`.

Use compact formatting, but never put slices in a table; maximum 80 lines. Never claim improvement without measurement.
The candidate chooses a slice ID when invoking Agent mode; do not assign per-slice
statuses. Return the plan; stop.
```
